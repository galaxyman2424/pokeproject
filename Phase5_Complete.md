# Phase 5 — Team Optimization Engine: Complete

## Overview

Phase 5 builds a genetic algorithm optimizer that evolves competitive Pokémon teams toward maximum expected performance against the current Gen 9 OU metagame. The optimizer wires together all previous phases — Phase 2 co-occurrence data for synergy scoring, Phase 4 threat analysis for structural evaluation, and Phase 6 battle simulation for empirical win rate estimation — into a single composite fitness function that scores and evolves teams over generations.

Three significant bugs were identified and resolved during development before the optimizer produced analytically valid results.

## Data Expansion

Before Phase 5 optimization could produce reliable results, the replay dataset was expanded from 423 battles to **3,480 battles** by increasing the Showdown replay API page count from 3 to 60 pages. The full ETL pipeline was re-run to ingest the new replays, and all Phase 2 analysis outputs (usage, move, item, tera, co-occurrence) were regenerated at the larger dataset size.

This was necessary because the viability scoring system (see below) requires a representative usage distribution — at 423 battles too many legitimate OU Pokémon had zero or near-zero appearance counts to produce reliable scores.

## OU Pool Generation

The optimizer draws candidate Pokémon from `data/ou_pool.json`, a flat list of species names generated by `data/dump_data.js` using the `@pkmn/dex` package.

### Bug Fix 1 — NFE and Pre-evolution Contamination

The initial pool contained 837 species including NFEs (not fully evolved), pre-evolutions, and unevolved babies (Gabite, Scorbunny, Ralts, etc.) because `@pkmn/dex` tiers these as "NU" or lower rather than marking them as battle-ineligible. Random teams generated from this pool were dominated by unusable Pokémon.

Fixed by adding two filters to `dump_data.js`:

```javascript
if (species.nfe) continue;         // skip not-fully-evolved
if (species.battleOnly) continue;  // skip forme aliases
```

Pool size after filtering: **474 fully-evolved, battle-legal species.**

## Fitness Function

```
composite = 0.4 × meta_matchup
          + 0.3 × synergy
          + 0.3 × simulation

fitness = composite × viability_multiplier
```

### Meta Matchup Score (weight: 0.4)

```python
meta_matchup = 1.0 - threat_score(analyze_threats(team))
```

Calls the Phase 4 threat analysis engine. `threat_score` returns 0.0–1.0 where lower means fewer structural threats. Inverted so higher is better. Captures type holes, role gaps, speed tier weaknesses, and archetype vulnerability.

### Synergy Score (weight: 0.3)

Average pair win rate across all C(6,2) = 15 Pokémon pairs on the team, sourced from `output/pair_cooccurrence.json` (Phase 2). Pairs not observed in the dataset default to 0.5 (neutral). Rewards teams whose members have historically won together in real ladder games.

### Simulation Score (weight: 0.3)

Win rate against a sample of real teams drawn from the database via `simulate_matchup()` (Phase 6). A fresh sample of opponent teams is drawn from the database at the start of each generation so the optimizer cannot overfit to a fixed opponent set. Uses the Showdown battle engine via Node.js subprocess — no websockets required.

### Viability Multiplier (hard multiplier, not weighted)

```python
scores  = [viability_scores.get(p, 0.1) for p in team]
avg     = sum(scores) / len(scores)
minimum = min(scores)
multiplier = 0.7 × avg + 0.3 × minimum
fitness = composite × multiplier
```

Pokémon not observed in the dataset at all receive a `0.1` baseline. Pokémon in the dataset are scored by their usage % normalized via square root scaling (see Bug Fix 3). The multiplier is a weighted blend of team average and minimum viability — this penalizes genuinely off-meta picks without letting one fringe-but-valid Pokémon crater an otherwise strong team.

## Bug Fixes

### Bug Fix 2 — Viability Min Collapse

**Problem:** The initial viability multiplier used `min()` across all 6 team members. A team of 5 top-meta Pokémon plus one legitimate but less-common Pokémon (e.g. Glimmora at 7% usage) had its entire fitness score multiplied by that single member's low viability score, producing fitness values around 0.20 even for genuinely strong teams.

**Diagnosis:** Checked viability scores for the best team produced after 50 generations:

| Pokémon | Usage % | Viability (linear) |
| :--- | :--- | :--- |
| Great Tusk | 24.86% | 1.000 |
| Ogerpon-Wellspring | 12.96% | 0.521 |
| Dragapult | 11.72% | 0.471 |
| Kyurem | 8.69% | 0.350 |
| Iron Moth | 8.15% | 0.328 |
| Glimmora | 7.08% | 0.285 |

`min()` = 0.285 → `0.73 × 0.285 = 0.208`. Score confirmed matching observed output.

**Fix:** Replaced `min()` with a weighted blend of average and minimum:
```python
multiplier = 0.7 × avg + 0.3 × minimum
```

### Bug Fix 3 — Linear Normalization Too Aggressive

**Problem:** Linear normalization (`usage / max_usage`) produced very low scores for all Pokémon except Great Tusk (the dominant outlier at 24.86% usage). Glimmora at 7% scored 0.285 despite being a top-tier hazard setter, because it was being compared against Great Tusk's outlier usage rather than the field.

**Fix:** Square root normalization softens the gap between top and fringe Pokémon:
```python
score = (usage_pct / max_usage) ** 0.5
```

With square root normalization, Glimmora scores `√0.285 = 0.534` — still lower than Great Tusk but no longer treated as a near-garbage pick.

## Genetic Algorithm

### Population Initialization

30 random teams drawn from the 474-species pool. Each team is 6 unique Pokémon.

### Selection

Tournament selection with k=4. Four candidates are drawn at random; the one with the highest fitness score advances as a parent.

### Crossover

A random core of 3 Pokémon is preserved from parent A. Remaining 3 slots are filled from parent B (members not already in the core). If parent B cannot supply 3 unique non-core members, the remainder is drawn from parent A.

### Mutation

With probability 0.3, one random team member is replaced with a random species from the pool not already on the team.

### Elitism

Top 10% of each generation (3 teams from a population of 30) carry over unchanged into the next generation. Prevents regression and ensures the best discovered teams are never lost.

### Resume / Persistence

Results are saved to `output/optimizer_results.json` after every generation. If the process is interrupted, re-running without `--no-resume` seeds the new population from the top third of the previous run's final generation. No progress is lost across overnight runs.

**Team analysis:**
- Great Tusk — hazard control (Stealth Rock + Rapid Spin), physical anchor

- Ogerpon-Wellspring — Water-type wallbreaker, Spikes synergy
- Raging Bolt / Iron Valiant — special offensive threats, speed control

The team covers Ground, Water, Fire, Electric, Dark, and Fighting offensively. Great Tusk handles hazard removal. No glaring type holes. Consistent with known Gen 9 OU balance/offense structures.

Score progression over 50 generations confirmed upward convergence — average score climbed from ~0.05 (generation 1, random pool) to ~0.40+ (generation 50, converged meta Pokémon).
